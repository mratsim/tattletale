# Lean verification backend: toolchain, reference model, and suites

Crucible's Lean verification backend (`src/codegen/backends/lean_lang.nim`) emits a Lean 4
verification module from a `{.global.}` kernel's post-pass IR. The model covers two kernel
shapes only and refuses everything else loudly:
the guarded thread (buffers `a` and `b` read, `output` written, guard `tid < literal`)
and the constant-bound loop with one indexed write (the axpy shape adds one uint32 scalar).

This directory holds the locked Lean project plus the suite tests.
The emitted modules elaborate against the project's lake environment.

## Layout

| Path | Role |
|---|---|
| `lean-toolchain` | locks `leanprover/lean4:v4.28.0`, honored by elan |
| `lakefile.lean` | the `crucible_lean` package, explicit roots, no glob |
| `ToolchainSmoke.lean` | toolchain gate: elaboration, typechecking, real proofs |
| `AddKernel.lean` | hand-written per-thread model of the add kernel, the byte-exact reference of the emitter test |
| `Negative.lean` | deliberately false claim, `lake env lean Negative.lean` must exit nonzero |
| `t_lean_emit.nim` | emitter end-to-end: elaboration, statement match, refusals |
| `t_lean_pragmas.nim` | verification pragmas: proven/unproven manifest, refusals |
| `t_lean_loop.nim` | loop-kernel emission and loop-invariant scaffolds |
| `t_lean_execute.nim` | axpy execution end-to-end: the emitted def runs on concrete inputs, values asserted in Nim |
| `lean_testutils.nim` | shared `elaborate` and `execute` helpers |
| `generated/` | emitted modules and manifests, gitignored, regenerated by the tests |

## Checks

```bash
cd tattletale
nim test_crucible_lean        # the four suites

cd workspace/crucible/tests/codegen/lean
lake build                    # must exit 0
lake env lean Negative.lean   # must exit nonzero
```

Notes:

- `lake env lean` is required, plain `lean` cannot find the built `.olean` files
- `Negative.lean` stays outside the lake roots, so the library build stays green

## Sorry hazard

- a `sorry` only warns, so elaboration exits 0 on an unproved scaffold
- every automated check must therefore run `lake env lean -DwarningAsError=true`,
  the form `lean_testutils.elaborate` uses
- the extraction manifest `<module>.manifest.json` beside each emitted module
  records the proven/unproven verdict, one entry per verification pragma
