# Lean verification backend: toolchain, reference model, and suites

Crucible's Lean verification backend (`src/codegen/backends/lang_lean.nim`) emits a Lean 4
verification module from a `{.global.}` kernel's post-pass CIRv2:

- the `lean:` macro joins through `cgLean` in `CodegenKind`, value normalizations, reshaping and bool-domain resolution only, no rename
- the model covers two kernel shapes only and refuses everything else loudly
- the guarded thread shape: buffers `a` and `b` read, `output` written, guard `tid < literal`
- the loop shape: one constant-bound loop with one indexed write, the axpy shape adds one uint32 scalar

Emitted modules default to the `<kernel>.autogen.lean` name. The suffix marks
machine-emitted modules against hand-written ones like `AddKernel.lean`.

Verification pragmas capture at proc level and extract into Lean scaffolds,
one per pragma name (`{.precondition:}`, `{.invariant:}`, `{.postcondition:}`):

- a precondition is assumed, carried as the hypothesis `h`
- an invariant is proved from the guard
- a postcondition attempts `simp [body, h]`

Settling elaborates the staged module through `lake env lean`:

- failing proofs downgrade to `sorry`-backed scaffolds, recorded unproven
  inside the extraction manifest `<module>.manifest.json`
- any refusal drops the staged file, nothing unverified stays on disk

This directory contains the locked Lean project and the suite tests.
Every test elaborates its emitted modules against the project's lake environment.

## Layout

| Path | Role |
|---|---|
| `lean-toolchain` | locks `leanprover/lean4:v4.28.0`, honored by elan |
| `lakefile.lean` | the `crucible_lean` package, explicit roots, no glob |
| `ToolchainSmoke.lean` | toolchain check: elaboration, typechecking, real proofs |
| `AddKernel.lean` | hand-written per-thread model of the add kernel, the byte-exact reference of the emitter test |
| `Negative.lean` | deliberately false claim, `lake env lean Negative.lean` must exit nonzero |
| `t_lean_emit.nim` | emitter end-to-end: elaboration, statement match, refusals |
| `t_lean_loop.nim` | loop-kernel emission and loop-invariant scaffolds |
| `t_lean_execute.nim` | axpy execution end-to-end: the emitted def runs on concrete inputs, values asserted in Nim |
| `t_lean_pragmas.nim` | verification pragmas: payload grammar, proven/unproven manifest, settling refusals |
| `t_lean_project.nim` | the locked project's checks as tests: `lake build`, ToolchainSmoke, Negative.lean |
| `lean_testutils.nim` | shared `leanIr`/`leanIrSpec` capture macros, `elaborate` and `execute` helpers |
| `generated/` | emitted modules and manifests, gitignored, regenerated by the tests |

## Checks

```bash
cd tattletale
nim test_crucible_lean        # the five suites

cd workspace/crucible/tests/codegen/lean
lake build                    # must exit 0
lake env lean Negative.lean   # must exit nonzero
```

Notes:

- `lake env lean` is required, a `lean` call without the lake environment cannot find the built `.olean` files
- `Negative.lean` stays outside the lake roots, so the library build stays green

## Sorry hazard

- a `sorry` only warns, so elaboration exits 0 on an unproved scaffold
- every automated check therefore runs `lake env lean -DwarningAsError=true`,
  the form `lean_testutils.elaborate` uses
- the extraction manifest `<module>.manifest.json` beside each emitted module
  records the proven/unproven verdict, one entry per verification pragma
